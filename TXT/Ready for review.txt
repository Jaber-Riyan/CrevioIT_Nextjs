Backend + Admin Dashboard for Crevio IT Website
Context
The site (crevio-nextjs, Next.js 15 App Router + React 19 + TS + Tailwind 4) is currently 100% static — all content lives in src/data/siteData.ts as hardcoded arrays, with icons stored as imported React components (LucideIcon / react-icons IconType). There is no database, API, or auth.

The goal: make every content block CRUD-manageable from a protected admin dashboard so non-developers can edit content without redeploying. This requires (1) a database + models, (2) a REST API, (3) admin-only authentication, (4) an image upload path, (5) an icon strategy that replaces "component references" with storable strings that the frontend resolves dynamically, and (6) refactoring the public site to read from the DB instead of siteData.ts.

Chosen stack (confirmed with user)
Backend: Next.js Route Handlers in the same app (src/app/api/**).
Database: MongoDB + Mongoose.
Media: UploadThing (uploadthing.com) — store returned file URLs/keys in Mongo.
Auth: Custom JWT + credentials (bcrypt-hashed), single seeded admin, httpOnly cookie.
Key design principle
Public pages (server components) read the DB directly via Mongoose query helpers (no HTTP round-trip) and pass data down to client section components as props.
The REST API exists primarily for the dashboard (interactive CRUD) and is guarded by auth.

Data models & TypeScript interfaces
Shared types live in src/types/content.ts and are the single source of truth; Mongoose schemas mirror them. Every icon field becomes an object of strings, never a component reference:

// Icon reference stored in DB and resolved on the client
export type IconRef = {
  library: "lucide" | "react-icons/si" | "react-icons/fa" | "react-icons/fa6"
         | "react-icons/di" | "react-icons/tb" | "react-icons/bi";  // extendable
  name: string;   // e.g. "Github" (lucide) or "SiReact" (react-icons)
  color?: string; // hex, e.g. "#61DAFB" — used by technologies/social
};

Icon strategy (the critical piece)
Today icons are component references — unstorable in a DB. We store IconRef strings and resolve them at render time with a single client component.

src/components/ui/DynamicIcon.tsx (client):

"use client";
import { lazy, Suspense, useMemo } from "react";
// map library string -> lazy module loader (whole subpackage lazy-loaded once)
const loaders: Record<string, () => Promise<any>> = {
  "lucide": () => import("lucide-react"),
  "react-icons/si": () => import("react-icons/si"),
  "react-icons/fa": () => import("react-icons/fa"),
  "react-icons/fa6": () => import("react-icons/fa6"),
  // ...extendable
};
export function DynamicIcon({ library, name, color, className }: IconRef & { className?: string }) {
  const Cmp = useMemo(() => lazy(async () => {
    const mod = await loaders[library]?.();
    const Icon = mod?.[name];
    return { default: Icon ?? (() => null) };
  }), [library, name]);
  return <Suspense fallback={<span className={className} />}>
    <Cmp className={className} style={color ? { color } : undefined} />
  </Suspense>;
}
Matches the user's described formats: react-icons/si + SiReact + #61DAFB; lucide + Github.
Section components stop doing const Icon = item.icon; <Icon/> and instead render <DynamicIcon {...item.icon} className="h-7 w-7" />.
Dashboard IconPicker: two selects/inputs (library + icon name) + a color input, with a live <DynamicIcon> preview so the admin sees the icon before saving. (Optional enhancement: searchable name list per library.)
API design
RESTful, one folder per resource. Standard shape:

GET /api/<resource> — list. Public callers get active/published only; authenticated admin gets all (detected via cookie).
POST /api/<resource> — admin only — create (zod-validated).
GET /api/<resource>/[id] — single.
PATCH /api/<resource>/[id] — admin only — update.
DELETE /api/<resource>/[id] — admin only — delete.
Optional PATCH /api/<resource>/reorder — bulk order update for sortable lists.
src/lib/api-helpers.ts provides requireAdmin(req) (verifies JWT cookie, 401 otherwise), a json() helper, and a try/catch wrapper mapping zod errors → 400. Every mutating handler calls requireAdmin first.

Auth routes:

POST /api/auth/login — validate {email,password} against AdminUser, bcrypt.compare, on success sign JWT and set httpOnly/secure/sameSite cookie.
POST /api/auth/logout — clear cookie.
GET /api/auth/me — return current admin or 401.
Uploads:

src/app/api/uploadthing/core.ts — file router with middleware that calls requireAdmin (only admins can upload), returns file {url,key}.
src/app/api/uploadthing/route.ts — exports the handler.
Dashboard ImageUploader uses @uploadthing/react; portfolio stores multiple {url,key}, blog stores one coverImage.
Authentication & protection
Hashing: bcryptjs in src/lib/auth/password.ts.
JWT: jose in src/lib/auth/jwt.ts (Edge-compatible — required because middleware runs on Edge). Payload { sub, email, role }, ~7d expiry.
Session: httpOnly + secure + sameSite=lax cookie (e.g. crevio_admin).
src/middleware.ts: matches /dashboard/:path*. Verifies the cookie's JWT; if invalid/absent → redirect to /login. (API mutation guards live in requireAdmin at the handler, not middleware, so public GETs stay open.)
Single admin: No public signup. scripts/seed.ts creates the admin from ADMIN_EMAIL/ADMIN_PASSWORD. "Only our admin can access" is satisfied by there being exactly one seeded account and no registration route.

Seed / migration
scripts/seed.ts (run once): connects to Mongo, creates the admin user, and imports every current siteData.ts array — translating each icon component to its IconRef. Example mappings: SiReact → {library:"react-icons/si", name:"SiReact", color:"#61DAFB"}, footer Globe2 → {library:"lucide", name:"Globe2"}. This guarantees zero content loss and gives immediate real data to build the dashboard against.
